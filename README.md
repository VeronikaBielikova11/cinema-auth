# Cinema API · автентифікація

Серверна частина кінотеатру на NestJS, PostgreSQL і TypeORM: фільми, зали, розклад сеансів і бронювання місць. Це продовження домашнього завдання №2, у якому з'явилися користувачі:

- реєстрація, вхід, пара токенів і ротація refresh-токена;
- access-токен (JWT) перевіряє власний глобальний guard, Passport.js не використовується;
- ролі `user` і `admin`: розкладом і довідниками керує лише адміністратор;
- бронювання належить користувачу з токена: своє можна скасувати, чуже не можна (адміністратор скасовує будь-яке);
- усі помилки мають єдину структуру `{ statusCode, message, error, path, timestamp }`.

## Встановлення

Потрібні Node.js 22.12 або новіший і Docker.

```bash
npm install
```

## Змінні середовища

Створіть файл `.env` у корені проєкту, наприклад скопіюйте зразок командою `cp .env.example .env`:

```dotenv
PORT=3000

DB_HOST=localhost
DB_PORT=5434
DB_USER=cinema
DB_PASSWORD=cinema
DB_NAME=cinema

JWT_ACCESS_SECRET=change-me-to-a-long-random-string-of-32-chars-or-more
ACCESS_TOKEN_TTL_MINUTES=15
REFRESH_TOKEN_TTL_DAYS=30

ADMIN_EMAIL=admin@example.com
ADMIN_PASSWORD=admin-password
```

| Змінна                     | Опис                                                                           | Обов'язкова       |
| -------------------------- | ------------------------------------------------------------------------------ | ----------------- |
| `PORT`                     | Порт, на якому слухає сервер                                                   | ні, типово `3000` |
| `DB_HOST`                  | Хост PostgreSQL                                                                | так               |
| `DB_PORT`                  | Порт PostgreSQL на хості                                                       | так               |
| `DB_USER`                  | Користувач бази                                                                | так               |
| `DB_PASSWORD`              | Пароль користувача                                                             | так               |
| `DB_NAME`                  | Назва бази                                                                     | так               |
| `JWT_ACCESS_SECRET`        | Секрет підпису access-токена, щонайменше 32 символи                            | так               |
| `ACCESS_TOKEN_TTL_MINUTES` | Час життя access-токена у хвилинах, від 1 до 60                                | так               |
| `REFRESH_TOKEN_TTL_DAYS`   | Час життя refresh-токена в днях, від 1 до 365                                  | так               |
| `ADMIN_EMAIL`              | Пошта адміністратора, потрібна лише для `npm run seed`                         | для seed          |
| `ADMIN_PASSWORD`           | Пароль адміністратора, щонайменше 8 символів, потрібен лише для `npm run seed` | для seed          |

Змінні проходять валідацію класом `EnvironmentVariables` ([src/config/env.validation.ts](src/config/env.validation.ts)): якщо змінних бракує або вони некоректні, застосунок не стартує. Docker Compose бере ті самі значення з `.env`. Порт `5434` обрано, щоб не конфліктувати з локальним PostgreSQL і базою попереднього домашнього завдання.

## Запуск

Підняти базу даних через Docker Compose:

```bash
docker compose up -d
```

Застосувати міграції:

```bash
npm run migration:run
```

Заповнити базу тестовими даними (адміністратор, 2 фільми, 2 зали, 4 сеанси в різні дати, 1 бронювання). Повторний запуск не створює дублікатів:

```bash
npm run seed
```

## Створення першого адміністратора

Через API адміністратора створити неможливо: реєстрація завжди видає роль `user`. Першого адміністратора створює `npm run seed` із пошти й пароля у змінних `ADMIN_EMAIL` та `ADMIN_PASSWORD`, пароль зберігається як хеш bcrypt. Запускайте seed на порожній базі після міграцій. Якщо користувач із такою поштою вже існує, його запис і роль не змінюються.

Після цього увійдіть через `POST /auth/login` із цими даними.

Запустити застосунок у режимі розробки:

```bash
npm run start:dev
```

Swagger доступний на [http://localhost:3000/docs](http://localhost:3000/docs).

## Міграції

| Команда                                                      | Що робить                                   |
| ------------------------------------------------------------ | ------------------------------------------- |
| `npm run migration:run`                                      | застосовує всі нові міграції                |
| `npm run migration:revert`                                   | відкочує останню міграцію                   |
| `npm run migration:show`                                     | показує, які міграції застосовано           |
| `npm run migration:generate -- src/database/migrations/Name` | генерує міграцію з різниці сутностей і бази |

Файл джерела даних для CLI TypeORM: [src/data-source.ts](src/data-source.ts). Міграції лежать у [src/database/migrations](src/database/migrations). Застосовану міграцію не редагують: зміна схеми означає нову міграцію. Міграція `AddAuth` видаляє наявні бронювання, бо колонка `user_id` обов'язкова, а власника в старих записів немає.

## Перевірка роботи

Файл [requests.http](requests.http) містить запит до кожного маршруту і на кожну описану помилку. Відкрийте його у VS Code з розширенням REST Client і виконуйте запити згори вниз: ідентифікатори підставляються зі змінних, очікуваний код відповіді вказаний у заголовку запиту.

Автоматичні тести (потрібна запущена база; тести створюють окрему базу `cinema_test` і не чіпають робочих даних):

```bash
npm run test:e2e
```

## Доступ до маршрутів

Access-токен передається в заголовку `Authorization: Bearer <token>`. У Swagger натисніть **Authorize** і вставте токен.

| Доступ                  | Маршрути                                                                                                                                                                                         |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Без токена              | `POST /auth/register`, `POST /auth/login`, `POST /auth/refresh`, `GET /films`, `GET /films/:id`, `GET /halls`, `GET /halls/:id`, `GET /showings`, `GET /showings/:id`, `GET /showings/:id/seats` |
| Будь-який авторизований | `POST /showings/:id/bookings`, `DELETE /bookings/:id`, `GET /bookings/my`, `POST /auth/logout`, `GET /auth/me`                                                                                   |
| Лише адміністратор      | `POST /films`, `PATCH /films/:id`, `DELETE /films/:id`, `POST /halls`, `DELETE /halls/:id`, `GET /bookings`, `POST /showings`, `GET /showings/:id/bookings`                                      |

`POST /auth/login` і `POST /auth/refresh` повертають `{ accessToken, refreshToken }`. `POST /auth/refresh` і `POST /auth/logout` приймають тіло `{ refreshToken }`.

## Схема бази даних

```
films ──┐                ┌── halls
        │ 1           1  │
        └──< showings >──┘          film_id, hall_id: ON DELETE RESTRICT
                │ 1
                ├──< bookings              showing_id: ON DELETE RESTRICT
                │        │ 1
                │        └──< booking_seats   booking_id: ON DELETE CASCADE
                └───────────<                 showing_id: ON DELETE RESTRICT

users ──< bookings          user_id: ON DELETE RESTRICT
users ──< refresh_tokens    user_id: ON DELETE CASCADE

UNIQUE (booking_seats.showing_id, row, seat)
```

- `booking_seats.showing_id` дублює сеанс бронювання навмисно: унікальний індекс будується по колонках однієї таблиці, тож саме база не дає продати місце двічі.
- У `refresh_tokens` лежить SHA-256 від токена, а не сам токен. Ротація споживає токен одним запитом `DELETE ... RETURNING`, тому з кількох одночасних запитів успішним буде лише один.
- Перелік місць залу в базі не зберігається, сервіс обчислює його з `rows` і `seats_per_row`.

## Структура

```
src/
├── auth/        вхід, токени, guards і декоратори доступу
├── users/       користувачі та хешування паролів
├── common/      спільні декоратори, pipe і глобальний фільтр винятків
├── config/      валідація змінних середовища
├── database/    налаштування підключення, міграції, коди помилок PostgreSQL
├── films/       операції з фільмами
├── halls/       операції із залами, обчислення переліку місць
├── showings/    операції із сеансами, розклад з посторінковою видачею
├── bookings/    бронювання та зайнятість місць на сеансі
├── data-source.ts  джерело даних для CLI TypeORM
└── seed.ts      заповнення бази тестовими даними
```

Залежності між модулями йдуть в один бік: `bookings → showings → films, halls`, `auth → users`. Guards `auth` реєструє глобально, тому інші модулі від нього не залежать.

## Домовленості

- `startsAt` зберігається в `timestamptz` і повертається в UTC, тому `2030-06-15T18:00:00+03:00` у відповіді стане `2030-06-15T15:00:00.000Z`. Фільтр `date` теж рахує добу за UTC.
- `GET /showings`: `page` від 1 (типово 1), `limit` від 1 до 100 (типово 20), `sort` — `asc` або `desc` за часом початку (типово `asc`). Сеанси з однаковим часом упорядковані за `id`. Фільтрація, сортування та обрізання сторінки виконуються в SQL-запиті.
- Видалити фільм чи зал, на який посилається сеанс, не можна: відповідь `409`. Перевірку робить зовнішній ключ `ON DELETE RESTRICT`.
- Якщо хоча б одне місце в запиті на бронювання зайняте, відповідь `409` і в базі не лишається ні бронювання, ні його місць. Текст помилки бази у відповідь не потрапляє.
- Неправильно сформований `:id` дає 404, як і неіснуючий, бо запису з таким id немає.
- Пошта приводиться до нижнього регістру, тому `A@x.com` і `a@x.com` це один обліковий запис. Пароль обмежений 72 символами, бо bcrypt ігнорує все, що йде далі 72 байтів.
- Поля, яких немає в DTO, мовчки відкидаються, запит через них не падає.
- Зал обмежений 1000 рядами і 1000 місцями в ряду, а ціна квитка 100 000 000 копійок. Рік випуску фільму не може бути раніше за 1888.
